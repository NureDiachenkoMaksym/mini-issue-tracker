## 2. Product purpose, actors та обмеження

SOURCE [S1 §0–2]: внутрішня вебсистема для реєстрації, відстеження та координації вирішення проблем програмного продукту в невеликій команді. Бізнес-мета — скоротити час від реєстрації проблеми до її призначення та вирішення.

SOURCE [S1 §1; §3 BR-01]: основні користувачі — Team Member і Team Lead. У першому релізі три заздалегідь визначені користувачі: два Team Member та один Team Lead. Product Owner і System Administrator — вторинні stakeholders, а не додаткові основні ролі MVP.

DERIVED [S1 §5 US-03; AC-07.4]: assignee — зв’язок користувача з конкретним issue, а не окрема глобальна роль. Team Lead також повинен бути поточним assignee, щоб змінювати status.

SOURCE [S1 §1 KC-01–KC-07]: невелика внутрішня команда; простий і швидкий у розробці перший реліз; web application; без зовнішніх клієнтів та інтеграцій із GitHub/GitLab/Jira; AI не обов’язковий для першого релізу, але має бути можливість подальшого розширення.

SOURCE [S1 §1 A-01–A-09, саме припущення]: одна команда; небагато користувачів і одночасних сесій; один assignee та один поточний priority; comments достатньо для обговорення; mobile application не потрібний; майбутній AI рекомендаційний, навчальних даних може бракувати. Припущення не перетворюються на додаткові функції.

## 4. Included User Stories та всі критерії приймання

Усі вимоги розділу 4 мають тип SOURCE; джерело кожного рядка — S1 §5, відповідна US та AC. Переклад зберігає зміст; джерельні ID не змінені.

### US-01 — Create Issue

Actor: автентифікований член команди. Мета: зареєструвати проблему з назвою та описом для подальшого відстеження.

| Source ID | Критерій |
|---|---|
| AC-01.1 | Користувач може ввести Title та Description. |
| AC-01.2 | Title обов’язковий. |
| AC-01.3 | Description обов’язковий. |
| AC-01.4 | Створена заявка отримує ID, status = Open, created_at, author. |
| AC-01.5 | Після створення priority не встановлено. |

SOURCE [S1 §5 US-01, Gherkin]: ID унікальний; author — поточний користувач. За порожнього Title заявка не створюється і показується «Title is required». Це альтернативні приклади тих самих AC, не додаткові критерії. «New Issue page» згадано в прикладі — modal є окремою UX-пропозицією D-01.

### US-02 — View Issues

Actor: автентифікований член команди. Мета: переглядати зареєстровані проблеми та поточні деталі.

| Source ID | Критерій |
|---|---|
| AC-02.1 | Авторизований член команди може переглядати список issues. |
| AC-02.2 | Кожний рядок містить щонайменше ID, Title, Status, Priority, Assignee, якщо призначений. |
| AC-02.3 | Можна вибрати issue зі списку та відкрити його деталі. |
| AC-02.4 | Деталі містять ID, Title, Description, Status, Priority, Assignee, якщо призначений, Author, Created at. |
| AC-02.5 | Якщо issues немає, показується порожній список або повідомлення про їх відсутність. |

### US-03 — Assign Issue to the responsible team member

Actor: Team Lead. Мета: призначити відповідального за виконання заявки.

| Вихідне посилання | Критерій |
|---|---|
| US-03, AC, пункт 1 | Можна вибрати одного assignee. |
| US-03, AC, пункт 2 | Assignee повинен бути членом команди. |
| US-03, AC, пункт 3 | Призначати заявку може лише Team Lead. |
| US-03, AC, пункт 4 | Поточний assignee відображається у заявці. |

Джерело не надає цим чотирьом пунктам окремих AC-ID.

### US-04 — Set Issue Priority

Actor: Team Lead. Мета: визначати пріоритетність роботи.

| Source ID | Критерій |
|---|---|
| AC-04.1 | Встановлений Priority має одне зі значень Low, Normal, High, Critical. |
| AC-04.2 | Встановлювати й змінювати priority може лише Team Lead. |

### US-05 — Track Issue Progress

Actor: член команди. Мета: бачити поточний прогрес роботи.

| Source ID | Критерій |
|---|---|
| AC-05.1 | Поточний status показано для кожного issue. |
| AC-05.2 | Status показано на сторінці issue. |
| AC-05.3 | Status показано у списку issues. |

### US-06 — Add Comment

Actor: член команди. Мета: обговорювати проблему в контексті заявки.

| Source ID | Критерій |
|---|---|
| AC-06.1 | Текст коментаря не може бути порожнім. |
| AC-06.2 | Доданий коментар зберігається й показується для відповідного issue. |
| AC-06.3 | Автор коментаря зберігається й показується. |
| AC-06.4 | Дата/час створення зберігаються й показуються. |
| AC-06.5 | Невдале збереження не створює коментаря та спричиняє повідомлення про помилку. |

### US-07 — Update Issue Status

Actor: поточний assignee. Мета: змінювати status, щоб команда бачила стан роботи.

| Source ID | Критерій |
|---|---|
| AC-07.1 | Нова заявка створюється зі status = Open. |
| AC-07.2 | Допустимі статуси: Open, In Progress, Resolved, Closed. |
| AC-07.3 | Новий status зберігається та показується під час наступного перегляду. |
| AC-07.4 | Користувач, який не є виконавцем заявки, не може змінити її status. |
| AC-07.5 | Система забороняє status поза визначеним переліком. |

### US-08 — View Important Open Issues

Actor: член команди. Мета: швидко знаходити важливі незакриті проблеми.

| Source ID | Критерій |
|---|---|
| AC-08.1 | High зі status, відмінним від Closed, входить до Important Issues. |
| AC-08.2 | Critical зі status, відмінним від Closed, входить до Important Issues. |
| AC-08.3 | Low та Normal не входять до Important Issues. |
| AC-08.4 | Closed не входить до Important Issues незалежно від priority. |

## 5. UI-релевантні бізнес-правила

| Тип / джерело | Зміст |
|---|---|
| SOURCE / S1 §3 BR-01–02 | Лише автентифіковані члени команди; кожний може створити issue. |
| SOURCE / S1 §3 BR-03; §5 AC-01.4 | Початковий status = Open; ID, author і час визначаються при створенні. |
| SOURCE / S1 §3 BR-04–05 | Початковий priority відсутній (Not Set); встановлені рівні — Low, Normal, High, Critical. |
| SOURCE / S1 §3 BR-06 | Керувати priority може лише Team Lead. Це правило не про assignee. |
| SOURCE / S1 §1 Open Questions; §5 US-03 | Призначення одного члена команди — лише Team Lead. |
| SOURCE / S1 §3 BR-07–08; §5 AC-07.4 | Чотири статуси; змінювати status може поточний assignee. |
| SOURCE / S1 §3 BR-08.1 | Лише Open → In Progress; In Progress → Resolved; Resolved → Closed; Resolved → In Progress. Інші переходи заборонені. |
| SOURCE / S1 §3 BR-09; BR-09 1.; §5 AC-08.1–4 | Important: High/Critical та status != Closed; Resolved ще не Closed і може входити до Important. У джерелі уточнення надруковане як «BR-09 1.»; далі позначено BR-09.1. |
| SOURCE / S1 §3 BR-10–11 | Видалення та окрема користувацька історія змін не передбачені. |
| SOURCE / S1 §5 AC-06.1–5 | Порожній comment заборонений; успішний містить author/time; failed save показує помилку без нового збереженого comment. |
| SOURCE / S1 §3 BR-12; §8 | AI-рекомендації — майбутній scope; не створювати їхні controls у MVP. |

DERIVED [BR-08.1]: Closed не має вихідних переходів; вибір поточного status не є переходом.

DERIVED [BR-08 + AC-07.4]: Team Lead non-assignee не змінює status. Якщо assignee відсутній, ніхто не може змінити status до призначення.

DERIVED [BR-04/05; AC-08.1–4]: відсутній priority не відповідає High/Critical, тому не входить до Important. Not Set — відсутність, а не п’ятий встановлений рівень; формат null/enum не визначений.

DERIVED [BR-08.1; US-04; US-06]: заборона переходів із Closed сама по собі не забороняє comments або зміну priority. Нові обмеження не додавати.

| NFR | Вимога | Що може показати дизайн | Що перевіряється лише реалізацією |
